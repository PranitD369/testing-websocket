# React PWA client (`web/`)

A second test client built as a React + TypeScript PWA. Hits the same `/ws` and
`/fallback/photo` endpoints as the vanilla client at `/`, but adds:

- A componentized UI with strict typed message handling
- `vite-plugin-pwa` (autoUpdate): web app manifest, service worker, installable on
  mobile and desktop, offline shell precache
- Update banner when a new SW version is available
- Browser proxy in dev so you can iterate on the React app at `localhost:5173`
  while the backend stays on `localhost:8080`

The vanilla client at `/` is kept untouched — quickest smoke test, no build step.

## Dev workflow

In one terminal:

```bash
DATABASE_URL=postgres://postgres:lab@localhost:5432/lab npm run dev
# Fastify on http://localhost:8080  (PORT in your .env)
```

In another:

```bash
cd web
npm install   # first time only
npm run dev
# Vite on http://localhost:5173 with HMR
```

Vite proxies `/ws`, `/fallback/*`, `/health` to Fastify so the React app behaves
as if it were served from the same origin. Open
<http://localhost:5173> in the browser — `sessionId` is stored in `localStorage`
just like the vanilla client.

## Production build

```bash
cd web
npm run build   # outputs to web/dist/
```

After the build, restart the Fastify server. It checks for `web/dist/` on boot
and registers a static handler at `/app/` plus a SPA fallback that rewrites
unknown `/app/*` GETs to `index.html` (so client-side navigation works on
reload).

Visit <http://localhost:8080/app/>.

## PWA behavior

- **Manifest** (`manifest.webmanifest`): `start_url=/app/`, `scope=/app/`,
  `display=standalone`. Installable from Chrome / Edge / Safari (iOS A2HS).
- **Service worker** (`sw.js`): precaches the JS/CSS/HTML shell so the page
  loads instantly on revisit, including offline.
- **Network exclusions**: the SW deliberately **never** caches `/ws/*`,
  `/fallback/*`, or `/health` — these must always hit the network. See
  `vite.config.ts: workbox.navigateFallbackDenylist`.
- **Auto-update**: `registerType: 'autoUpdate'` + the in-app banner. When the
  SW detects a new bundle on revisit, the banner offers "Reload" to swap in.
- **Offline fallback**: when the SW is registered and offline, the static
  shell still loads. Live audio still requires connectivity (the SW does
  not pretend the WS works offline) — the in-app `Photo Fallback` panel is the
  recovery path when streaming is impossible.

## Icons

The PWA needs raster PNG icons for installability (SVG-only manifests fail
Chrome's installability check). Since the container doesn't have a native
rasterizer (`rsvg-convert` / Inkscape / ImageMagick), `scripts/generate-icons.mjs`
emits solid-color circle PNGs using only Node's built-in `zlib` and `Buffer`.
Replace them with real designer assets before shipping.

To regenerate:

```bash
cd web
node scripts/generate-icons.mjs
```

## What this validates about the backend

- The Fastify backend works identically whether the client is vanilla JS or
  built from Vite — confirming there's no client-build coupling on the server
  (a sign the proxy contract is clean).
- The PWA exercises the same reconnection / mode-change / photo-fallback paths
  as the vanilla client, so the React reliability story matches the backend's:
  `sessionId` survives an install + page-close because it's in `localStorage`,
  and the cached transcript summary on the server picks the conversation back up.
- Service worker precaching + manifest installability put the lab on equal
  footing with the production app described in the job posting ("React PWA +
  Fastify backend"), so the same test rig can be installed on a phone and
  driven from an actual cellular network.
